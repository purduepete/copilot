Copilot CLI

How GitHub Copilot CLI makes me more productive — its capabilities beyond skills, and the proactive WorkLog system built on top of them. Captured 2026-06-26.

Topic: The Copilot Toolbox

Skills are just one layer. Copilot CLI offers several "resources," each suited to a different job.

1. Capabilities & when to use each

Capability What it is Best for
Memory /memory Cross-session facts about me Defaults & preferences I shouldn't have to repeat (e.g. "lunch = lunch/personal").
Skills /skills Triggered procedures + judgment Multi-step tasks with conventions (worklog, calendar).
Custom instructions Always-on rules loaded every session Global conventions & session-start behavior (no trigger needed).
MCP servers /mcp Tools the model calls directly Letting any AI surface drive my tools (e.g. WorkLog).
Scheduled prompts Recurring autonomous prompts (cron/interval) Proactive automation — nudges, end-of-day checks.
Subagents / fleet /fleet Parallel delegated work Running independent tasks at once.
Session store Copilot's record of everything we've done "What did I work on?" reconciliation against my own history.
Voice /voice Dictation Hands-free logging.
Plan / Research /plan /research Structured deep work Big tasks & investigations.

2. Key concepts to leverage

  • Context window — the working memory of a session; manage it with /context and /compact.
  • Mechanism vs judgment — put deterministic checks in scripts/tools; leave conversational judgment to skills. (Overlap detection is code; "which item did you mean?" is the skill.)
  • Loaded ≠ executed — a custom instruction is context I read and apply on my next turn; it is not a literal session-start hook.
  • Per-session schedules — scheduled prompts belong to one session/machine and die when it closes; re-arm via an always-on instruction.

3. The customization stack

The real power is combining layers into one workflow:

memory (knows my defaults) + scripts (deterministic mechanism) + instructions (always-on behavior) + scheduled prompts (proactive trigger) + git (cross-machine sync).

Topic: Proactive WorkLog

Flips WorkLog from reactive (acts when asked) to proactive (checks in on a clock).

1. What it does

  • End-of-day check — weekdays 6 PM: shows any running task + untracked gaps, offers the close-out routine.
  • Hourly nudge — weekdays 10 AM–5 PM: silent unless something needs attention (long-running task, idle untracked time, or gaps).

The deterministic brain is Check-WorkLogStatus.ps1, which returns a nudge verdict with reasons. Thresholds: long task ≥ 150 min, idle ≥ 30 min, gaps ≥ 10 min. It never changes WorkLog without confirmation.

2. Auto-arm across machines

Scheduled prompts are per-session, so they are re-armed at the start of every session by an always-on instruction: 

~/.copilot/instructions  -->  (junction)  -->  worklog_web/instructions/worklog-proactive.instructions.md

The repo is the sync bus: git pull delivers the instruction + scripts to all 3 machines (same junction pattern as skills). On a new machine, create the junction once: 

git -C C:\Files\Dev\main\worklog_web pull
New-Item -ItemType Junction -Path "$env:USERPROFILE\.copilot\instructions" `
  -Target "C:\Files\Dev\main\worklog_web\instructions"

3. Viewing & managing

I want to… Say…

4. Gotchas

Scheduled prompts do NOT appear under /tasks (that panel shows only subagents & shell commands). View them by asking "list my schedules."
  • Schedules only fire while a Copilot session is open; close the terminal and they pause until the next session re-arms them.
  • Two open sessions = two armed copies = brief double nudges. Harmless; close one to dedupe.

Topic: WorkLog AI Workflows

Helper scripts (in worklog_web/src) that the worklog skill calls to reduce manual entry.

1. Smart defaults

Suggest-WorkDefaults.ps1 infers category / project / ADO id for a task title from my own history (exact > prefix > token match). The skill infers before asking, and only asks when there's no match.

2. Gap detection

Find-WorkGaps.ps1 finds untracked spans (≥ 10 min) inside the work day. Triggers: "find gaps", "untracked time", "what did I miss". Also runs automatically as part of the end-of-day routine.

3. Calendar import

Import-CalendarDay.ps1 turns a day's Outlook meetings into WorkLog entries — one-shot, preview → confirm → apply. Keeps only organized/accepted, busy, already-started meetings; skips all-day OOO, free/tentative/declined and personal non-meeting blocks. Infers project from history and dedupes against existing entries. Triggers: "import my calendar", "log my meetings". Use -OpenDay to back-fill a past day that has no start-of-day marker.

4. Session mining

Reconstruct what I worked on from an AI session and create tasks for the untracked parts:

  • VS Code chat → Get-VSCodeWork.ps1 -Folder <repo> — parses Copilot Chat transcripts.
  • Copilot CLI session → Get-CopilotWork.ps1 — parses ~/.copilot/session-state/*/events.jsonl (default: all of today's sessions; -Current for the live one).

Both chunk the session into blocks on idle gaps (-GapMinutes) and present a numbered table; pick one, then -Create -Block <ID> logs it with the block's exact start/end. Non-overlap boundary: both scripts subtract the day's already-tracked WorkLog entries first, so proposed blocks fall only in untracked time — a block straddling a logged span is split or dropped (-AllowOverlap to disable). Shared logic lives in worklog_web\src\WorkBlocks.psm1.

Time Tracking

Topic: Time-Tracked Log

A conversational, cloud-hosted work log. I tell Copilot when I start, switch, and finish work (and what I accomplished); it timestamps the sessions and rolls them into a daily standup, weekly summary, and an interactive dashboard. Driven by the worklog skill.

1. How to use

Just talk to Copilot — it infers IDs, times, and flags and updates the dashboard. For example:

Starting on the MS Sales pull, work item 435324.
Switching to a review meeting.  (the pull stays open)
Done with the pull — patched the view, validated counts. Blocked on prod approval.
Give me my standup.  /  Start work log (opens the live dashboard).

2. Common phrases

I describe what I did; Copilot maps it to the right command. The most-used ones:

What I say What it does
“Starting work on <thing>” / “Now on the MS Sales pull, ADO 435324” opens a session (start)
“Log my work since the last item” start -AfterLast (chains from the last end, no overlap)
“Switching to item 3” / “Back on the pull” switch (never closes anything)
“Done with item 3 — <accomplishment>” stop (optional -Blocker)
“Close item 3 against gh issue 17” close — gh note + stop + dashboard, one shot
“Add a note to item 5: <text>” tasknote (note on a session)
“Remember <text>” / “Note for July 1: <text>” note (standalone, date-bound)
“Edit item 5: category dev / retitle / set project” edit
“Standup” / “Wrap up the week” / “Status” / “Start work log” standup / week / status / serve
“Switch to my home profile” profile home
“List my profiles” / “What profiles do I have?” profile -List
“Create a profile <name>” profile <name> -Create
“Rename profile <old> to <new>” profile <old> -Rename <new> (moves all its data)
“Delete profile <name>” profile <name> -Delete (dry run) → -Yes to confirm; guarded

3. Direct CLI

I can also drive it without Copilot. Entry point: C:\Files\Dev\main\worklog_web\cli\wl.ps1. 

$wl = "C:\Files\Dev\main\worklog_web\cli\wl.ps1"
pwsh -File $wl startday
pwsh -File $wl start "Fix MS Sales pull" -Ado 435324 -Category development -Project webportfolio
pwsh -File $wl switch -Id 1
pwsh -File $wl stop  "Patched view, validated counts" -Id 1 -Blocker "Need prod approval"
pwsh -File $wl close "Fixed formatting" -Id 1 -Issue 17 -RepoPath C:\Files\Dev\main\webportfolio -CloseIssue
pwsh -File $wl note  "Renew ADO PAT before it expires" -Date 2026-07-01
pwsh -File $wl summary "High-level recap of the day"
pwsh -File $wl status                 # what's open
pwsh -File $wl standup                # / week  / dashboard  / log -Days 14
pwsh -File $wl serve                  # prints the hosted dashboard URL (no local server)
pwsh -File $wl endday
pwsh -File $wl status -Profile home
  • -Category = kind of work (development, meeting, review…); -Project = which product/app. Both are dashboard columns.
  • switch moves focus and never closes a session; stop closes one with an accomplishment; close bundles gh-issue note + stop + dashboard in one shot.
  • Back-dating: -At <datetime> on start/stop, or edit -Id <n> -Start <dt> -End <dt>. start -AfterLast chains from the previous session's end.

4. Locations

  • Reports: daily standup, weekly summary, and an interactive calendar dashboard (HTML + Markdown to paste).
  • Parallel sessions: start/switch never close another session — they stay open until I stop them.
  • Profiles: work (links ADO) and home keep separate logs; -Profile <name> overrides per command, profile home sets this machine's default.
  • State: cloud-hosted (Azure Functions + SQL); the CLI authenticates via az account get-access-token.

5. Managing profiles

Profiles keep separate logs (e.g. work, home). The CLI supports full lifecycle — list, create, rename, and delete — via the profile command: 

$wl = "C:\Files\Dev\main\worklog_web\cli\wl.ps1"
pwsh -File $wl profile                         # show this machine's default profile + bounds
pwsh -File $wl profile home                    # set this machine's default profile
pwsh -File $wl profile -List                   # all profiles with row counts (sessions/notes/…)
pwsh -File $wl profile side -Create            # create a new profile
pwsh -File $wl profile side -Rename hobby      # rename (moves all of its data)
pwsh -File $wl profile hobby -Delete           # DRY RUN — shows what would be deleted, deletes nothing
pwsh -File $wl profile hobby -Delete -Yes      # actually delete it (and ALL its data)
Delete guardrails. Deletion is strict and irreversible: it cascades to all of that profile's data (sessions, task-notes, notes, commentary). A bare -Delete is a dry run that only previews the row counts — nothing is removed without -Yes. The CLI refuses to delete the active/default profile (switch to another first) and refuses to delete the last remaining profile; deleting a nonexistent profile errors.
  • Names must match ^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$ (URL-safe, no spaces).
  • Reads never create profiles — viewing ?profile=X on the dashboard no longer resurrects an empty ghost row.
  • Start/end-day markers + time-bound constraints apply only to the work profile; home has no start/end-day concept (bounds default off — see the worklog-profile skill).

Topic: Mining VS Code Chats for Tasks

VS Code stores Copilot Chat history as plain *.jsonl files on disk, so Copilot CLI can read them to reconstruct what I worked on — useful when I didn't log as I went.

1. Reconstruct work from chats

The worklog_web\src\Get-VSCodeWork.ps1 helper turns a workspace's chat history into time-stamped work blocks I can log or close. Just ask Copilot:

Show me the work I completed today (table: ID, work, start, end), then I'll pick one to log.
Log what I worked on in the last hour. 
$g = "C:\Files\Dev\main\worklog_web\src\Get-VSCodeWork.ps1"
pwsh -File $g -Folder C:\Files\Dev\main\webportfolio -Json   # today's blocks (ID | work | start | end)
pwsh -File $g -LastMinutes 60 -Create                        # fuzzy "what was I just doing", log it
  • Chats live under %APPDATA%\Code\User\workspaceStorage\<hash>\ (the transcripts\*.jsonl mirror is easiest to parse); workspace.json maps the hash back to the project path. Insiders uses Code - Insiders.
  • Blocks split on idle gaps (-GapMinutes, default 90) and are back-dated to their real start when logged.
