Azure DevOps

Topic: Open Work Item Report

Quick reference for regenerating my open Azure DevOps work item list as an HTML report.

1. How to regenerate

Option A — Ask Copilot (easiest). In any new Copilot session, just type:

Regenerate my ADO work item list

Copilot has stored memories about the script and will run it automatically.

Option B — Run it myself (no Copilot needed). Open a terminal and run:

pwsh -File C:\Files\Dev\main\work\copilot\Generate-OpenWorkItems.ps1

This regenerates and opens the report in the browser.

2. What gets produced

  • Output file: C:\Files\Dev\main\copilot\open-work-items.html
  • Contents: all work items assigned to me that are not Closed / Done / Removed / Resolved
  • Layout: grouped by Area → Status, sorted by Changed date (oldest → newest)
  • Columns: Changed, Project, ID, Type, Status, Task (with clickable ADO links)
  • Features: color-coded status badges + live search/filter box

3. Useful options

Include Resolved items too:

pwsh -File C:\Files\Dev\main\work\copilot\Generate-OpenWorkItems.ps1 -Exclude Closed,Done,Removed

Generate without auto-opening the browser:

pwsh -File C:\Files\Dev\main\work\copilot\Generate-OpenWorkItems.ps1 -NoOpen

Write to a different file:

pwsh -File C:\Files\Dev\main\work\copilot\Generate-OpenWorkItems.ps1 -OutFile C:\temp\items.html

You can also ask Copilot for variations, e.g. "regenerate but include Resolved".

4. Setup / troubleshooting

  • Org: https://dev.azure.com/StarlightAgileBI
  • Auth: uses my existing Azure login — no PAT needed. If the script errors with a token problem, run az login.
  • Why counts fluctuate during cleanup: the script uses stable single-condition WIQL to get IDs, then strongly-consistent point-reads of each work item. This avoids the unreliable counts that ADO's multi-condition WIQL returns while its query index lags behind live edits.

Time Tracking

Topic: Time-Tracked Log

A conversational, time-tracked work log. I tell Copilot when I start work (and what it is), when I switch, and when I finish (and what I accomplished). It records timestamped sessions and rolls them up into a daily standup and weekly summary — as HTML (to view) and Markdown (to paste into Teams / email / ADO).

1. How to use (via Copilot)

The intended way to use this is to just talk to Copilot. For example:

Starting on the MS Sales pull, work item 435324.
Switching to a review meeting.  (the pull stays open)
Back on the pull.
Done with the pull — patched the view, validated counts. Blocked on prod approval.
Give me my standup.  /  Wrap up the week.

Copilot has stored memories about this framework and will call the right functions to log work and generate reports.

2. Talking to Copilot (phrases)

I don't need exact syntax or item numbers — I just describe what I did and Copilot infers the IDs, timestamps, and flags, then regenerates the dashboard. Things I can type:

3. CLI commands

I can also drive it directly without Copilot:

pwsh -File C:\Files\Dev\main\copilot\worklog\Work.ps1 start "Fix MS Sales pull" -Ado 435324 -Category Dev -Project webportfolio
pwsh -File C:\Files\Dev\main\copilot\worklog\Work.ps1 start "Architecture review" -Category Meeting
pwsh -File C:\Files\Dev\main\copilot\worklog\Work.ps1 switch -Id 1
pwsh -File C:\Files\Dev\main\copilot\worklog\Work.ps1 tasknote "Found root cause in the view definition"
pwsh -File C:\Files\Dev\main\copilot\worklog\Work.ps1 note "Renew ADO PAT before it expires" -Date 2026-07-01 -Category followup
pwsh -File C:\Files\Dev\main\copilot\worklog\Work.ps1 notes
pwsh -File C:\Files\Dev\main\copilot\worklog\Work.ps1 summary "High-level, fuzzy recap of the day's accomplishments"
pwsh -File C:\Files\Dev\main\copilot\worklog\Work.ps1 stop  "Patched view, validated counts" -Id 1 -Blocker "Need prod approval"
pwsh -File C:\Files\Dev\main\copilot\worklog\Work.ps1 edit  -Id 1 -Status paused -Category Dev -Project webportfolio
pwsh -File C:\Files\Dev\main\copilot\worklog\Work.ps1 edit  -Id 1 -Start "2026-06-16 14:00" -End "2026-06-16 15:30"
pwsh -File C:\Files\Dev\main\copilot\worklog\Work.ps1 stop  "Aligned on structure" -Id 7 -At "2026-06-16 16:23"
pwsh -File C:\Files\Dev\main\copilot\worklog\Work.ps1 close "Fixed comma formatting" -Id 1 -Issue 17 -RepoPath C:\Files\Dev\main\webportfolio -CloseIssue
pwsh -File C:\Files\Dev\main\copilot\worklog\Work.ps1 status
pwsh -File C:\Files\Dev\main\copilot\worklog\Work.ps1 standup
pwsh -File C:\Files\Dev\main\copilot\worklog\Work.ps1 week
pwsh -File C:\Files\Dev\main\copilot\worklog\Work.ps1 dashboard
pwsh -File C:\Files\Dev\main\copilot\worklog\Work.ps1 log -Days 14
pwsh -File C:\Files\Dev\main\copilot\worklog\Work.ps1 dashboard -Profile personal
  • start opens a session (ad-hoc unless -Ado <id> is given). Other open sessions stay open.
  • -Category classifies the kind of work (Dev, Meeting, Review…); -Project tags which product/app it belongs to (e.g. webportfolio, webbookmarks). Both show as their own dashboard columns.
  • switch -Id <n> moves focus — it never closes anything.
  • stop closes the current session (or -Id <n>) with an accomplishment and optional -Blocker.
  • close — one-shot finish (new): bundles the whole “close a work item” flow into a single process: optional GitHub-issue note + stop + one dashboard rebuild (instead of separate note/stop/dashboard calls). Pass -Issue <n> to fetch the issue once and attach the standard note [#N Title](url) - milestone | state | commit, -RepoPath <dir> to resolve the repo for the gh/commit lookup, and -CloseIssue to also gh issue close it. Runs in <2s; supports -At, -Blocker, -Status like stop. Note: the dashboard already auto-rebuilds on every change, so a separate dashboard call after a mutation is redundant.
  • summary "<text>" sets the day's high-level, fuzzy recap shown under the dashboard summary stats (below “Showing”).
  • edit -Id <n> changes any field of a logged session after the fact (only the fields you pass); -Reopen clears the end time.
  • Back-dating — forgot to log in real time? -At <datetime> on start/stop, or edit -Id <n> -Start <dt> -End <dt> to fix an existing session's times. Or just tell Copilot “I forgot to log 2–3pm, I was doing X in Dev” and it inserts the session.
  • start -AfterLast (new): back-dates the new session's start to the most recent session's end — perfect for “log my work since the last item” with no overlaps and no manual lookup of the previous end time.

4. Standup, weekly & dashboard reports

  • Work dashboard → work-dashboard.html: a modern, interactive view of the whole log with an navigable month calendar — days with logged work are highlighted; click one to filter the table to that date. Includes live summary stats (total time, sessions, time by category) and a sortable, grouped session table. Uses the Roboto Flex font. Sessions are grouped by day and numbered per date (each day restarts at 1), with a dedicated Project column beside Category and uniformly aligned columns across every day.
  • Daily standup → standup.html + standup.md: Yesterday (accomplishments + time), Today (in progress / planned), Blockers.
  • Weekly summary → weekly-summary.html + weekly-summary.md: accomplishments grouped by day, total time, time by category, and blockers.
  • Standup & weekly are written as both styled HTML (to view) and Markdown (to paste). The HTML opens automatically unless I ask not to.

5. How it works

  • Parallel sessions: starting or switching never closes another session — they stay open until I explicitly stop them.
  • Time tracking: start/stop timestamps give duration per session, rolled up per item, per day, and per category.
  • ADO or ad-hoc: link an ADO work item by ID (auto-linked in reports), or log meetings / reviews / support with a -Category.
  • Project tagging: -Project <name> records the product/app a session belongs to as a first-class field (previously embedded in the item title in brackets/parentheses).
  • Notes: timestamped log entries I capture while working, rolled into the reports.
  • IDs vs the “#” column: every session has a durable, globally-unique id (immutable for its lifetime — shown in the “#” cell tooltip and used by -Id). The “#” shown in the dashboard is just a per-day display number (each day restarts at 1), computed at render time — renumbering the view never touches the stored ids.
  • State persists in work-log.json, so the log survives across sessions. Saves are atomic (staged to a .tmp file, then swapped in) and keep a one-deep .bak rollback copy, so a crash mid-write can’t corrupt the log (both are git-ignored).

6. Work vs personal profiles

The tool is portable (all paths resolve from its own folder, so it runs wherever the purduepete/copilot repo is cloned) and profile-aware — each profile keeps its own log and reports under worklog\data\<profile>\, so work and personal entries never mix.

  • Profiles are defined in worklog.config.json (e.g. work links ADO items; personal has no org).
  • Which profile is active resolves in this order: -Profile <name> on a command → WORKLOG_PROFILE env var → the git-ignored .profile file in the worklog folder → the config default → work.
  • Work.ps1 profile shows the active profile; Work.ps1 profile personal sets this machine's default.
  • On another computer: clone purduepete/copilot, run worklog\Work.ps1 profile personal once, then pull/push to sync the personal log.

Switching between work and personal — three ways, least to most permanent:

# 0. Which profile am I on?
pwsh -File C:\Files\Dev\main\copilot\worklog\Work.ps1 profile

# 1. One command only (-Profile wins over everything else):
pwsh -File C:\Files\Dev\main\copilot\worklog\Work.ps1 dashboard -Profile personal

# 2. This shell window only (env var):
$env:WORKLOG_PROFILE = 'personal'
pwsh -File C:\Files\Dev\main\copilot\worklog\Work.ps1 status
$env:WORKLOG_PROFILE = ''          # back to machine default

# 3. This computer's default (persists in the git-ignored .profile):
pwsh -File C:\Files\Dev\main\copilot\worklog\Work.ps1 profile personal
pwsh -File C:\Files\Dev\main\copilot\worklog\Work.ps1 profile work

Typical setup: the work computer stays on work; the personal computer is set once to personal so you never have to think about it. A -Profile flag always overrides the default for that one command.

7. VS Code integration

Two ways to track time while working in VS Code. A reusable template lives at worklog\vscode\ (tasks.json, keybindings.jsonc, README.md).

  • Talk to Copilot in the integrated terminal (recommended): run the GitHub Copilot CLI in VS Code's terminal and describe what you're doing — Copilot maps it to the right command (see “Talking to Copilot (phrases)” above).
  • Tasks + keybindings (no Copilot needed): copy worklog\vscode\tasks.json into a workspace's .vscode\tasks.json, then run Ctrl+Shift+P → Tasks: Run Task → WorkLog: … (Start / Switch / Note / Stop / Daily summary / Status / Dashboard / Standup). Tasks prompt for title / category / id / text.
  • Optional chords: paste worklog\vscode\keybindings.jsonc into your user keybindings.json — e.g. Ctrl+Alt+W then S = Start, X = Stop, N = Note, M = Daily summary, T = Status, D = Dashboard.
  • Path: the template references Work.ps1 via a WORKLOG env var at the top of tasks.json — edit it if the repo is cloned elsewhere.
  • Note: true “track-as-you-type” automation (idle detection, per-file time) needs a dedicated extension such as WakaTime; this framework is intentionally explicit so sessions map cleanly to ADO items, meetings, and categories.

Topic: Mining VS Code Chats for Tasks

VS Code stores Copilot Chat history as plain files on disk. Copilot (CLI) can read those transcripts to reconstruct what I worked on and roll it up into high-level tasks — useful at the end of a coding session when I didn't log work as I went.

1. What this is

Every Copilot Chat session in VS Code is persisted locally (no cloud fetch needed). Because the files are on disk, Copilot CLI can open them, parse the user prompts and assistant turns, and summarize the work into time-tracked log entries or a standup.

2. Where chats live on disk

PathPurpose
%APPDATA%\Code\User\workspaceStorage\<hash>\chatSessions\*.jsonlPer-workspace chat sessions (incremental-patch JSONL)
%APPDATA%\Code\User\workspaceStorage\<hash>\GitHub.copilot-chat\transcripts\*.jsonlCleaner mirror transcript (one JSON event per line: session.start, user.message, assistant.turn_start…)
%APPDATA%\Code\User\workspaceStorage\<hash>\chatEditingSessions\Edit-session state for chats that changed files
%APPDATA%\Code\User\globalStorage\emptyWindowChatSessions\*.jsonlChats from a window with no folder open
%APPDATA%\Code\User\workspaceStorage\<hash>\workspace.jsonMaps the <hash> folder back to the actual project path

Insiders builds use %APPDATA%\Code - Insiders\ instead of %APPDATA%\Code\.

3. How to read them

The transcripts\*.jsonl mirror is the easiest to parse — each line is a JSON event with a type and data. To find which session a message belongs to, search across all chat files for the text, then resolve the workspace via workspace.json:

# Find a chat by remembered text, with its workspace folder
$root = "$env:APPDATA\Code\User\workspaceStorage"
Get-ChildItem $root -Recurse -File -Include *.jsonl |
  Select-String -SimpleMatch 'hello again' -List |
  ForEach-Object {
    $hash = ($_.Path -replace [regex]::Escape($root+'\'),'').Split('\')[0]
    $ws = Get-Content "$root\$hash\workspace.json" -Raw | ConvertFrom-Json
    "{0}`n  -> {1}" -f $_.Path, $ws.folder
  }

The richer chatSessions\*.jsonl uses an incremental-patch format (line 0 is the base object; later lines patch it), so for quick reads prefer the transcripts mirror.

4. Turning chats into tasks

Once parsed, I ask Copilot to summarize a coding session into high-level tasks and, optionally, log them:

Parse my VS Code chats from today and create high-level tasks for what I worked on.
Read the chat for the <project> workspace and log it as a work session.

Copilot reads the transcripts, groups the work into themed high-level tasks, and can write them straight into the time-tracked log (start/stop) and regenerate the dashboard.

Selectable work-block table (new): when I say “show me work completed today”, Copilot runs Get-VSCodeWork.ps1 -Json for the workspace and presents a numbered table — ID | work performed | start | end. I then just pick an ID and Copilot creates or closes a work item against that exact block (using its real start/end times):

# Today's blocks for a workspace, machine-readable
pwsh -File C:\Files\Dev\main\copilot\worklog\Get-VSCodeWork.ps1 -Folder C:\Files\Dev\main\webportfolio -Json

# Or a specific date / idle-gap threshold (blocks split on gaps > GapMinutes, default 90)
pwsh -File C:\Files\Dev\main\copilot\worklog\Get-VSCodeWork.ps1 -Folder C:\Files\Dev\main\webportfolio -Date 2026-06-18 -GapMinutes 60

# Fuzzy "what was I just doing" window (last 60 min) — and log it straight away
pwsh -File C:\Files\Dev\main\copilot\worklog\Get-VSCodeWork.ps1 -LastMinutes 60
pwsh -File C:\Files\Dev\main\copilot\worklog\Get-VSCodeWork.ps1 -LastMinutes 60 -Create

Copilot Skills

Topic: Personal Skills

Reusable capability packs that teach Copilot my recurring workflows, so a short natural request triggers the right action the same way every session — no re-explaining.

1. What skills are

  • A skill is a folder with a SKILL.md file: YAML frontmatter (name + when-to-trigger description) plus markdown instructions Copilot loads on demand.
  • Mine are user-level (under ~/.copilot/skills/), so they work in any repo and are personal — teammates don't see them.
  • Copilot picks the matching skill from the intent of my message; I don't have to name it.

2. My skills

SkillSay something like…What it does
worklog "log lunch 12–12:30", "start work on X", "create task ending at 12:00", "start work log" Drives the WorkLog CLI (Work.ps1) — start/stop/switch/add/edit/note, dashboards, live-edit server. Encodes my conventions: capitalize first word, chain back-filled tasks from the last entry's end time, fix typos and tell me.
ado-worklist "Regenerate my ADO work item list" Runs Rebuild-OpenWorkItems.ps1 (~4 s) to refresh open-work-items.html — my open items (assigned to @Me, excluding Closed/Done/Removed/Resolved), grouped by Area → Status, sorted by ID.
calendar "what meeting am I in?", "what's my next meeting?", "read my calendar" Reads the local Outlook calendar via the COM API (no Graph/login). Reports subject, time, organizer, Teams join link and agenda; filters out all-day OOF/OOO entries; can hand a meeting to the worklog skill to log it.

3. Activating & maintaining

  • Enable: run /skills in Copilot to view and toggle them.
  • Load new/edited skills: run /restart — skills are picked up at startup.
  • Edit: change the relevant SKILL.md; the WHEN: trigger phrases live in the frontmatter description.
  • Author a new one: ask Copilot to create a skill, or copy an existing folder as a template.
